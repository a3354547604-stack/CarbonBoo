# 附录 D · 验收清单（v4.1）

> **用法**：每完成一个模块，回到本附录勾选对应条目；全部勾选即达"可交付"状态。
> **判定原则**：能**现场操作证明**才算通过；只有"代码里写了"不算通过。
> **关联**：主计划书 **§16 的 A1–A18** 是总门槛（**定义在那里**），本附录是它们的展开与操作化（对照索引见 §11）。
> **v4.1 口径**：赛题二 **9 项官方要求全部实现**（5 项主要功能 F1–F5 ＋ 4 项创新拓展 I–Ⅳ）；**服务端是必做件**（账号 + 云端同步 + 取价 + 云端备份），其上的 **Web 后台管理端才是可选项**（ADR-0001）。

---

## §0 使用方式

1. 每个测试组独立执行：用**演示数据**（`rawfile/demo/demo-seed.json`，90 天约 260 条）测有数据场景，用"清空数据后"测空态。
2. 每条结果三选一：`✅通过` / `❌不通过（记问题）` / `⏭暂缓（记原因）`。
3. 涉及数值的（**§3 手算样例**、§4 一致性）必须**手算比对**，不接受"看起来对"。
4. **同步类（D6-x、§7.1）必须两台设备/模拟器实测**：云端通路用**同一账号**登录两台设备；近场通路用**两台已配对设备**。单机自说自话不算通过。
5. 测试环境记录：设备/模拟器型号、API 版本、构建号、日期。
6. 因子库与公式以 **APPENDIX-A** 为唯一依据；本附录所有样例的因子值必须与附录 A §2 逐位一致。

## §3 碳计算手算样例（对照 D1-8）

**公式（v4.0，无修正系数）**：`减排量(kgCO₂e) = 活动量 × 因子值`；`积分 = round(减排量 × 100)`。
**存储**：`reduction_kg` 保留 **4 位小数**；**积分基于 4 位小数后的值计算**。
**列名口径**：`期望积分` 列 = **应得 C**；**实际入账 A = max(0, min(C, 200 − D))**（见 §3.2），当日 D > 0 时以 A 为准。
**因子值来源**：APPENDIX-A §2（本表出行类一律取"净减排因子"列）。

### 3.2 封顶样例（对照 D3-3，口径见 PLAN §9.4）

**设定**：当日已有记录类流水合计 `D = 150` 分。

| 情形 | 应得 C | 已得 D | 实入 A = max(0, min(C, 200−D)) | `capped` | 界面提示 |
|---|--:|--:|--:|:--:|---|
| 再记一笔 96 分 | 96 | 150 | **50** | `1` | 「本次应得 96 分，今日剩余额度 50 分，已按 50 分入账」 |
| 再记一笔 30 分 | 30 | 150 | **30** | `0` | 无 |
| D 已 200，再记 | 96 | 200 | **0** | `1` | 「今日记录积分已达上限」 |
| D 已 200，完成目标 S1 | 20（目标） | 200 | **20** | — | 目标奖励**不封顶**、不计入 D |
| 记一笔 < 0.005 kg | round → 0 | — | — | — | 碳记录可存，**不生成积分流水** |

**D 的取数口径（必须严格一致）**

```sql
SELECT COALESCE(SUM(points), 0) FROM point_record
 WHERE user_id = ?
   AND occurred_at BETWEEN 今日00:00:00 AND 今日23:59:59
   AND source_type = 'carbon_record'                -- 记录类：含 record / record_capped / reverse
   AND is_deleted = 0
```

### 7.2 冲突（LWW）判定手算

```
T0: A 创建记录 R（updated_at = 1000）
T1: A 修改 R（updated_at = 2000, 值 = 1.9200 kg）
T2: B 修改 R（updated_at = 3000, 值 = 0.5760 kg）
→ A 合并：本地(2000) vs 远端(3000) → 远端更新 → A 采用 0.5760 kg；冲突 +1
→ B 合并：本地(3000) vs 远端(2000) → 本地更新 → applied，不变
结果：两端均为 0.5760 kg（updated_at 较新者胜）
平局（updated_at 完全相同）：按 deviceId 字典序较大者胜，保证两端收敛到同一值
时钟校正：比较前先按 offsetMs 归一到同一时间基准
```

## §9 演示数据规格（`demo-seed.json`）

**用途**：路演不空场 + 看板性能测试。**总数约 260 条，覆盖 90 天**：
> 本节是**全仓库演示数据规格的唯一来源**（`GLOSSARY.md` §内容与演示 与 `APPENDIX-E` §1 只引用本表，不重复数字）。
> **求和口径只有一处**：下面的表格只给"频率 + 单条量级"，**总量一律以 §9.1 汇总口径为准**；
> §10.3 的 `summary.csv` 示例与 §9.1 逐字同源（改一处必须同时改另一处）。

| 类别 | 频率 | 90 天条数 | 单条量级（按「日均新增减排 ≈0.7 kg」缩放后的**每条约值**） |
|---|---|---|---|
| 绿色出行 | 0.8 条/天 | ~72 | 骑行 1.5 km（0.2880）、步行 1.5 km（0.2880）、公交 2 km（0.3040）、地铁 1.85 km（0.2997）、拼车 4.2 km（0.3024）——单条 ≈**0.30 kg** |
| 节水节电 | 1.2 条/天 | ~108 | 节电 0.26–0.35 kWh（0.1483–0.1996）、节水 90–120 L（0.0151–0.0202）——单条 ≈**0.13 kg** |
| 旧物回收 | 0.5 条/天 | ~45 | 废纸 0.33 kg（0.2970）、废塑料 0.2 kg（0.3000）、废钢铁 0.25 kg（0.3000）、废铝 0.033 kg（0.2970）——单条 ≈**0.30 kg** |
| 光盘行动 | 0.4 条/天 | ~36 | 1 餐（0.3500）——单条 **0.35 kg** |

> ⚠️ **「单条量级」列是量级参考，不是求和依据。** v4.0 起本表曾写"典型值 = 骑行 5 km（0.9600）…"，
> 那组数与本文下面四条约束**数学上不可能同时成立**：单是 72 条出行按 0.9600 就是 69.12 kg ≈ 6,912 分，
> 再加水电/回收/光盘会到 300 kg 以上。**v4.2 起该列一律是上表的"缩放后每条约值"**，
> 与 `DemoService`（`app/entry/src/main/ets/viewmodel/DemoService.ets` 的 `dayPlan/travelItem/…`）逐条一致。

### §9.1 汇总口径（演示数据的**唯一求和来源**）

| 项 | 口径值 | 复算式 |
|---|---|---|
| 记录数 | **约 260 条 / 90 天** | 72 + 108 + 45 + 36 = **261**（规格统一表述为「约 260 条」，±1 条不构成偏差） |
| 日均新增减排 | **≈0.70 kg/天** | 0.8×0.30 + 1.2×0.13 + 0.5×0.30 + 0.4×0.35 = **0.701 kg/天** |
| 累计减排 | **≈61.74 kgCO₂e**（落在 60–90 区间，**恒 < 100 kg**） | 72×0.3000 + 108×0.1300 + 45×0.3000 + 36×0.3500 = 21.6000 + 14.0400 + 13.5000 + 12.6000 = **61.7400** |
| 记录类积分（毛） | **≈6,174 分** | 61.74 × 100；日均 ≈68.6 分 < 200 → **封顶不生效**（演示数据里没有 `record_capped`） |
| 积分余额 | **4,820–4,919**（在 4,000–6,000 区间内） | 播种收尾按目标余额 `TARGET_BALANCE = 4820` 反算一笔碳普惠兑换（`DemoService.exchangePlan`：`coins = floor((兑换前余额 − 4820) / 100)`）；兑换后余额必落 [4820, 4919] |
| 碳币 | = 收尾那笔兑换数（`MAX_COINS = 48` 封顶） | 见 §9 分布要求第 5 条 |
| 自动解锁徽章 | **6 枚** | 累计 < 100 kg ⇒ `B_TOTAL_100` 不触发；`B_TREE` 留给现场 |

> **四条约束为何相容（v4.2 收敛）**：① **约 260 条 / 90 天** ← 频率复算 261；
> ② **60–90 kg** ← 单条量级 × 频率 = 日均 ≈0.7 kg ⇒ 累计 **61.74 kg**（且 < 100 kg 硬上限，否则 `B_TOTAL_100` 会自动解锁、与"故意留 2 枚"冲突）；
> ③ **4,000–6,000 分** ← 记录类毛收益 ≈6,174 分**不等于最终余额**：余额由收尾兑换收敛到 **4,820 附近**，
> 所以"余额 4,000–6,000"与"累计 60–90 kg"并不矛盾（二者不是同一个量的两种写法）；
> ④ **6 枚自动解锁** ← 见上。

**分布要求**

1. **连续记录长度**：包含一段 **32 天连续**（用于解锁 `B_STREAK_30`）+ 若干 3–6 天短段（还原真实感）。
2. **徽章状态**：自动解锁 6 枚（`B_FIRST`、`B_STREAK_7`、`B_STREAK_30`、`B_TOTAL_10`、`B_GREEN_TRIP`、`B_RECYCLER`），**故意留 2 枚**（`B_TOTAL_100`、`B_TREE`）供现场解锁。
3. **累计减排**：**≈61.7400 kgCO₂e**（§9.1 汇总口径；恒 < 100 kg，不触发 `B_TOTAL_100`）。
4. **积分余额**：**4,820–4,919**（§9.1 汇总口径；足够现场买 1–2 个头像框并演示碳币兑换）。**注意：不再为"兑换植树证书"预留额度**（该商品已删除）。
5. **碳普惠**：预置 **1 条**已兑换碳币记录（= §9.1 收尾那笔兑换），便于现场直接演示"碳币 → 权益"。
6. **任务状态**：今日目标留 2 项未完成（现场演示完成动作）。
7. **分享**：无预置 `share_record`（现场生成更真实）。
8. **时间**：以"播种当天"为基准倒推 90 天，`occurred_at` 分布在各天 7:00–21:00。
9. **用户隔离**：演示数据 `user_id = 'demo-user'`；关闭演示模式时按该 id 清除。
