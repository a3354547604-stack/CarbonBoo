## 第 1 章 · 项目定位与最终目标

### 1.1 一句话定位

**碳小布是一款运行在 OpenHarmony 上的个人碳账本应用**：把日常低碳行为（出行、节水节电、旧物回收、光盘行动）量化成减排量与碳积分，用**目标、徽章、碳小铺**三层激励帮用户把低碳习惯坚持下去。

### 1.2 形态

| 项 | 内容 |
|---|---|
| 主形态 | OpenHarmony **手机应用**（单机版，离线全功能） |
| 加分形态 | **鸿蒙分布式多设备协同**（官方定义的创新加分项；无需账号、无需云） |
| 可选演示件 | **独立 Web 后台管理端**（FastAPI + MySQL，浏览器访问，用于商品定价与云端备份演示） |
| 不涉及 | 南向硬件、开发板、传感器、真实碳普惠平台对接（仅模拟）、真实支付 |

### 1.3 "做完了长什么样"（12 条验收画面）

1. 新用户**不联网、不注册**即可完成全部 5 个官方主要功能模块的操作，数据全部落在本机。
2. 录入一笔行为后，**1 秒内**在首页、记录页、看板页三处同时反映（同一数据源，无重复计算）。
3. 看板支持日/周/月/年四个粒度、折线/柱状/饼三种图表，切换粒度不重建页面。
4. 积分**账本可追溯**：任意一条积分流水都能回溯到产生它的碳记录或购买记录。
5. 达成目标时**自动结算**并弹提示；同一目标在同一周期内不会重复发分。
6. 用户可在**碳小铺**用积分购买头像框；购买后永久拥有、不可重复购买。
7. 用户可备份/恢复/导出（JSON + CSV）；恢复后记录数、积分数、徽章数、已购商品数完全一致。
8. **两台设备配对后**，在 A 机新记的一笔、新购的头像框，B 机能收到；同步面板显示"设备列表 / 最后同步时间 / 冲突记录数"。
9. **科普专栏**12 篇图文**离线可读**，支持分类、搜索、阅读进度与收藏。
10. **端侧 AI 识图**：选一张照片 → 给出候选低碳行为 → 用户确认后预填表单；识别不可用时自动落到"图标网格快速录入"。
11. **碳普惠模拟**：积分可按 `100 分 = 1 碳币` 兑换模拟权益，界面**全程强制标注"模拟演示"**。
12. **社交分享**：可将减排成果生成为分享卡片（含累计减排、等效换算、已解锁徽章），默认不含任何身份信息。

### 1.4 名词表（全文档统一口径）

| 名词 | 含义 | 易混淆点 |
|---|---|---|
| **碳记录** | 一条低碳行为记录（出行/节水节电/回收/光盘） | 不是"积分记录" |
| **减排量** | 该条行为避免的二氧化碳当量，单位 kgCO₂e | 由因子库算出，**必准** |
| **积分** | 激励货币，可买头像框 | 由减排量换算而来，**可封顶** |
| **目标** | 达成后发积分的任务（10 个） | 不是"徽章" |
| **徽章** | 长期荣誉（8 枚），**不发积分、不花钱** | 与积分体系完全独立 |
| **头像** | 8 个内置插画，**全部免费、默认投放** | 不可上传、不用收集 |
| **头像框** | 套在头像外的装饰圈，**8 个，用积分购买** | 与头像无关 |
| **主题** | 界面配色方案，当前仅 1 套免费默认主题 | 商品位保留，实现待定 |
| **碳小铺** | 用积分购买外观商品的页面 | 不做真实支付 |
| **碳币** | 碳普惠模拟体系中的虚拟币，`100 积分 = 1 碳币` | **模拟演示**，不可提现、不对接真实平台 |
| **碳普惠** | 官方创新项 3 的"模拟城市碳普惠接口" | 本项目**只做模拟接口**，界面强制标注 |
| **分布式协同** | 用鸿蒙分布式数据服务在多设备间同步数据 | 与"云账号同步"是两套东西，本项目**不建云账号体系** |
| **识图录入** | 端侧 AI 从照片推断低碳行为类别 | 只给候选，**必须用户确认**，不自动保存 |

## 第 3 章 · 开发铁律

> 这 4 条是全项目的最高约束。**任何一行代码与之冲突，改代码，不改铁律。**
> v4.0 起由 6 条收敛为 4 条：原「周期内只领一次」「零硬编码」降级为普通规范，分别见 §9.5 与 §15.2（因为引入端侧 AI 接口后必须允许少量不可避免的字面量）。

### 铁律 1 · 本地优先
**本机 `relationalStore` 是唯一真相源。** 分布式协同与云端只做"搬运"，不参与业务计算。未配对、无网络状态下，**除「设备协同 / 登录 / 碳小铺在线取价」外全部功能必须可用**。

### 铁律 2 · 单一计算入口
减排量计算**只能**在 `CarbonService.calculate()` 里发生。任何页面、任何组件**禁止**自己乘因子。

### 铁律 3 · 因子快照
每条碳记录保存时，**把当时的因子值、因子版本、来源一并存下来**。因子库以后升级，历史记录永不改写。

### 铁律 4 · 积分单向可追溯
**余额 = 收入合计 − 支出合计**。积分流水**只增不删**（删除靠冲正 `reverse`）。任何一条流水都能回溯到产生它的碳记录 / 目标 / 购买 / 碳币兑换；任何时刻可全量对账。

## 第 4 章 · 技术栈选型

### 4.1 客户端

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | **ArkTS**（TypeScript 超集） | 禁用 `any`，禁用 `@ts-ignore` |
| UI | **ArkUI 声明式**，Stage 模型 | `@Entry` / `@Component` / `@State` / `@Prop` / `@Link` / `@Provide` |
| 目标 API | **API 12**（`compileSdkVersion: 12`、`compatibleSdkVersion: 12`、`runtimeOS: OpenHarmony`） | 官方硬性要求 |
| 本地数据库 | **`@ohos.data.relationalStore`**（SQLite） | **19 张表**，见附录 B |
| 轻量配置 | **`@ohos.data.preferences`** | 主题、头像框、演示模式开关、deviceId |
| 分布式协同 | **`@ohos.distributedDeviceManager`** + **`@ohos.distributedDataObject`** + **`@ohos.distributedKVStore`** | 创新项 1：设备发现/组网、跨设备数据对象、跨设备 KV 同步 |
| 网络（可选） | **`@ohos.net.http`** | 仅用于后台取价与云端备份，**全应用唯一网络出口**：`common/HttpClient.ets` |
| 图表 | **ArkUI `Canvas` 自绘** | **不引第三方图表库** |
| 图片选择 | **`@ohos.file.picker`**（识图功能） | 无相机权限时不阻塞主流程 |
| 端侧 AI | **端侧推理接口 + NAPI 封装**（`AiAssistService`） | **接口层先行 + 假数据兜底**；模型可后换 |
| 定时提醒 | **`@ohos.reminderAgentManager`** | 智能服务：个性化任务推送 |

> **不引入任何第三方 npm/HAR 包**（图表、Markdown 渲染、网络均自研）。理由：构建稳定、无供应链风险、评审友好。

### 4.2 服务端

| 项 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | **Python 3.11 + FastAPI** | 自带 `/docs` 交互文档，路演可直接展示 |
| ASGI 服务器 | **Uvicorn**（`uvicorn main:app --workers 2`） | 2C2G 上 2 worker 足够 |
| ORM | **SQLAlchemy 2.x + PyMySQL** | 同步模式，够用且简单 |
| 数据库 | **MySQL 8.0** | 2C2G **必须调参**，见 4.3 |
| 鉴权 | **JWT**（`python-jose`）+ 密码哈希（`passlib[bcrypt]`） | 用户侧与管理侧两套 token |
| 参数校验 | **Pydantic v2** | 请求/响应模型 |
| 配置 | **`.env` + `pydantic-settings`** | 不入库、不进版本控制 |
| 后台前端 | **Jinja2 模板 + 原生 HTML/CSS/JS** | 不引前端框架，避免构建链 |

### 4.3 MySQL 在 2 核 2G 上的必要调参

> 不调参直接装 MySQL 8 会吃掉 600MB+ 内存，加上 Uvicorn 与系统开销容易 OOM。

```ini
# /etc/mysql/mysql.conf.d/mysqld.cnf
[mysqld]
innodb_buffer_pool_size = 256M
innodb_log_file_size    = 64M
max_connections         = 30
performance_schema      = OFF
table_open_cache        = 200
tmp_table_size          = 16M
max_heap_table_size     = 16M
```

**容量预期**：2C2G 上 MySQL(≈400MB) + Uvicorn(≈150MB) + 系统(≈400MB) ≈ 950MB，留有充分余量。

| 客户端依赖 | 服务端要求 |
|---|---|
| API 12 `@ohos.net.http` | HTTP/1.1，JSON over HTTPS（开发期允许 HTTP） |

### 5.3 四条关键数据流

**A. 记录一笔低碳行为（客户端，核心路径）**

```
用户填表 → RecordEditPage
  → 读因子：CarbonFactorRepository.getFactor(category, subType)
  → 预览：CarbonService.calculate({type, amount, unit, occurredAt})
        reductionKg = amount × factorValue          // dry-run，仅预览
  → 用户确认 → CarbonService.save(record)          // 开启事务
        ├─ insert carbon_record（含因子快照）
        ├─ PointService.awardForRecord(record)      // 受每日 200 分封顶约束
        ├─ GoalService.evaluate(userId, now)        // 可能结算目标分
        ├─ BadgeService.evaluate(userId)            // 可能解锁徽章（不发分）
        ├─ CarbonIncludeService.syncQuota(userId)   // 刷新碳币可兑换额度
        └─ commit
  → 返回 Result{ reductionKg, pointAwarded, capped, newGoals, newBadges }
```

**B. 打开看板**

```
DashboardPage
  → StatisticsService.aggregate(userId, granularity, range)
        ├─ 查 carbon_record 按区间聚合
        └─ 返回 { trend[], byCategory[], composition[], stats{} }
  → Canvas 组件按数据重绘（不重建页面）
```

**C. 多设备协同（鸿蒙分布式，创新项 1）**

```
DistributedPage → DistributedService.startSync()
  1. discover：DistributedDeviceManager 列出已配对设备
  2. attach  ：DistributedDataObject 绑定同步会话（sessionId = userId）
  3. merge   ：逐表 LWW（updated_at 大者胜；is_deleted 传播；id 幂等）
  4. 封顶口径：以本机已知流水判定；同步后发现超额**不追回**，仅冲突计数 +1
  5. 写 sync_log；成功才更新 device_info.last_sync_at
```

**D. 端侧 AI 识图录入（创新项 2）**

```
RecordEditPage → 点「拍照/选图」
  → AiAssistService.recognize(uri)
        ├─ 可用：返回 AiRecognizeResult{ recognized, category, subType, confidence, candidates[] }
        ├─ 不可用/超时（>3s）：recognized = false
        └─ 无论成败：图片**不落盘、不上传**，识别完即释放
  → 命中 → 预填类别与建议数量（**必须用户确认后才保存**）
  → 失败 → 落到「图标网格快速录入」降级路径
```

## 第 7 章 · 模块规格

### 7.1 行为核算引擎（F1-*）

**输入模型**（录入向导两步）
- 步骤 1：选大类（出行 / 水电燃气 / 回收 / 光盘）→ 选子类卡片。
- 步骤 2：填数量（带单位后缀与合理范围校验）+ 选时间（默认现在，可改往日）+ 可选备注。
- **快捷入口**：录入页顶部有「📷 识图录入」入口（见 7.11）与「图标网格快速录入」降级入口。

**计算规则（唯一口径）**

```
减排量(kgCO2e) = 活动量 × 因子值
```

- **无修正系数**（用户决策：不做保守/标准/积极档位；附录 A §3.1 同步删除 `correctionFactor`）。
- **因子库规模**：**30 个因子**，其中 **20 个 `recording: true`** 进录入表单（覆盖出行 7 / 水电燃气 5 / 回收 6 / 光盘 2），另 10 个只做科普对照与等效换算（附录 A §2）。
- 出行：活动量 = 距离(km)；公交/地铁按"同等里程燃油车"替代基准（见附录 A §2 说明）。
- 水电燃气：活动量 = 用量（kWh / L / m³）。
- 回收：活动量 = 质量(kg) 或件数(件，用平均质量换算)。
- 光盘：活动量 = 餐次(次)。
- 结果**保留 4 位小数存储**，展示保留 2 位小数（<1 kg 展示 3 位）。
- 积分 = `round(减排量 × 100)`，受第 9 章封顶规则约束。

**因子快照**：每条记录同时写入 `factor_value`、`factor_version`、`factor_source`、`confidence`。

### 7.11 端侧 AI 识图录入（创新项 Ⅱ，风险项）

**接口层先行 + 假数据兜底**（用户决策）：本模块先交付**稳定接口 + 可替换实现**，模型能力后补。

```ts
// 唯一对外接口
export interface AiRecognizeResult {
  recognized: boolean;          // 是否识别成功
  category?: string;            // travel | utility | recycle | plate
  subType?: string;             // 因子 subType，如 bicycle / bus / waste_paper
  confidence?: number;          // 0~1
  candidates?: AiCandidate[];   // 候选列表（最多 3 个，按置信度降序）
  engine: string;               // 'mock' | 'napi-model'，便于排查
}
export interface AiCandidate { category: string; subType: string; confidence: number; }
```

**实现策略（两段式）**
1. **阶段一（本期交付）**：`AiAssistService.recognize()` 走**假数据兜底实现**——按图片尺寸/文件名哈希稳定映射到一个候选，`engine = 'mock'`；接口、UI、数据流全部真实接通。
2. **阶段二（可后补）**：只替换 `AiAssistService` 内部实现为 NAPI 端侧推理，**上层页面、ViewModel、数据流一行不改**。

**约束**
- 图片**不落盘、不上传**，识别完即释放；请求相册仅读一次。
- 识别结果**只做预填**，**必须用户确认后**才保存记录。
- 超时阈值 **3 秒**；超时或不可用 → `recognized = false`。
- **必有的降级路径**：失败后展示「图标网格快速录入」，一步进入录入向导。
- 可能占用相机权限时，`module.json5` 才追加 `ohos.permission.CAMERA`；**不做相机也可用**（仅选图）。

**7.13.2 生活建议（5 条优先级规则，每日至多 1 条主建议）**

## 第 9 章 · 积分体系（核心规则）

### 9.1 总则

- **换算口径：1 kgCO₂e = 100 分。**
- 积分是一本**只增不减的流水账**（`point_record`），每条流水记录：时间、类型、分值、来源 ID、备注。
- **余额 = 收入合计 − 支出合计**（铁律 4）。
- **记录类收入当天封顶 200 分**；目标奖励不封顶；**不存在每日总额上限**。

### 9.2 收入规则

**R1 · 记录碳行为（封顶项）**

**判定依据（v4.0 决策「甲」）**：封顶判定**不再读 `point_daily_stat`**，改为从 `point_record` **实时聚合**：

```
今日已得 D = SELECT COALESCE(SUM(points), 0) FROM point_record
             WHERE user_id = ?
               AND occurred_at BETWEEN 今日00:00 AND 今日23:59:59
               AND source_type IN ('record', 'record_capped')
               AND is_deleted = 0
应得 C = round(减排量 × 100)          // 四舍五入，最小 1 分（减排量 ≥ 0.005 kg 时）
实入 A = max(0, min(C, 200 − D))
capped = (A < C)
```

> **两个 WHERE 条件都是必需的**：
> - 必须带 `source_type IN ('record','record_capped')`：否则 `goal`（目标奖励，不封顶）会被算进 D 导致记录分提前封顶；`purchase` / `carbon_include`（负数支出）会把 D 拉低，变相突破封顶。
> - 必须带 `is_deleted = 0`：排除冲正流水（编辑记录产生的差额头）。

| 场景 | 行为 |
|---|---|
| 当天已得 < 200 且加上本笔 ≤ 200 | **全额入账**，类型 `record` |
| 当天已得 < 200 但加上本笔 > 200 | **按剩余额度入账**，类型标记 `record_capped`，界面提示"今日记录积分已达上限" |
| 当天已得 ≥ 200 | **不再发放**记录类积分（记录本身照常保存），类型 `record_capped` 且 `points = 0` |
| 超出部分 | **不结转、不补发** |

**`point_daily_stat` 降级为纯展示缓存**
- 用途：首页 / 看板展示加速。
- 权威性：**派生可重算**（可整表删除后重建），**不参与封顶判定**、**不参与同步**。
- 维护：每次写入 `point_record` 的**同一事务内**增量更新。
- 必须提供 `PointService.rebuildDailyStat(userId)` 全量重建。
- 验收 A5 增加一条：**校验 `point_daily_stat` 与流水聚合结果一致**。

**R2 · 达成目标（不封顶）**

- 10 个目标各自独立，**在周期内只能结算一次**。
- **满足条件即自动结算**（不设手动领取按钮），结算后弹提示。
- 目标奖励**不计入** R1 的 200 分封顶。

**R3 · 其他**

- **徽章不发积分。**
- **不做**签到、邀请、看广告等任何其他得分途径。

### 9.3 支出规则

**R4 · 碳小铺购买**
- 支出 = 商品价格，产生一条**负数流水**（类型 `purchase`）。
- **已拥有商品不可重复购买**（按钮变"已拥有"并置灰）。
- 购买后**永久拥有**，`user_purchase` 参与分布式同步。
- **不允许透支**：余额不足时购买按钮不可点。
- **不退款、不回收。**

**R5 · 碳普惠兑换（模拟）**
- 支出 = 碳币数 × 100 分，产生一条**负数流水**（类型 `carbon_include`），并写一条 `carbon_include` 记录。
- **单向不可逆**：碳币不能换回积分。
- **不允许透支**：可兑换额度 = `floor(余额 / 100)`，达不到 1 碳币时按钮置灰。
- 不计入 R1 的 200 分封顶（它是支出，不是记录收入）。

### 9.4 展示口径（三处差异是有意为之）

| 位置 | 显示内容 |
|---|---|
| 记录保存成功提示 | 「本次减排 0.96 kgCO₂e，获得 **96** 积分」；被封顶时追加「（今日记录积分已达上限）」 |
| 首页积分小卡 | **余额** + **今日已获得**（记录分 + 目标分） |
| 碳小铺顶部 | **可消费余额** |
| 我的 → 积分明细 | 逐条流水：时间 / 类型 / 分值 / 备注 / 关联跳转 |

**流水类型枚举**：`record`（记录得分）、`record_capped`（封顶后部分得分/零得分）、`goal`（目标奖励）、`purchase`（碳小铺购买支出）、`carbon_include`（碳普惠兑换支出）、`reverse`（冲正，如编辑记录产生的差额）。

### 9.5 幂等与事务约束（防作弊）

1. **积分发放与减排量计算在同一事务内完成**，不允许"先记录后补分"。
2. **同一条 `carbon_record` 只产生一条得分流水**（`UNIQUE(source_type, source_id, type)` 约束）；编辑记录时产生 `reverse` 冲正流水而非改原流水。
3. **同一个目标在同一周期只产生一条 `goal` 流水**（`source_id = goalId + periodKey` 唯一）。
4. **分布式协同的封顶口径（v4.0 决策「甲2」）**：**以"本机已知的流水"判定封顶**；同步完成后若发现当天总量超过 200，**不追回**已发分，仅在协同面板**冲突计数 +1**。
   > 否决了"同步后回溯生成 `reverse` 负流水"的方案：会导致"积分无缘无故变少"，体验差且逻辑复杂。
5. **同一件商品只有一个购买流水**（`UNIQUE(user_id, item_id)`），重复购买必须被拒绝。
6. 跨设备协同时分值的权威来源是**产生该记录的那台设备**，对端只接受不重算。

### 9.6 数值平衡（设计依据）

| 项 | 数值 |
|---|---|
| 典型单日记录得分 | 4 笔共约 799 分 → **受封顶约束实得 200 分** |
| 典型单日目标奖励 | 约 55 分（S1+S2+S3） |
| **典型单日合计** | **约 255 分** |
| **典型单月合计** | **约 7,650 分** |
| 集齐 8 个头像框总价 | 51,000 分 → **约 7 个月**（活跃用户） |

|---|---|---|
| **单机态** | 未配对 / 未组网 | **全部功能可用**（含碳小铺用内置默认价）；协同页显示"未配对设备"与配对引导 |
| **协同态 · 已配对** | 已组网 + 对端在线 | 全部功能 + 跨设备同步 + 家庭碳积分合并视图 |
| **协同态 · 设备离线** | 已配对但对端离线 | 全部功能可用（写本机）；协同页显示"对端离线，恢复后自动同步" |

### 12.2 协同技术方案

| 能力 | 使用的 API | 用途 |
|---|---|---|
| 设备发现与组网 | `@ohos.distributedDeviceManager` | 列出可配对设备、发起配对、查询在线状态 |
| 跨设备数据对象 | `@ohos.distributedDataObject` | 会话级实时数据同步（`sessionId = userId`） |
| 跨设备 KV 同步 | `@ohos.distributedKVStore` | 结构化数据的跨设备落盘与合并 |
| 本机落盘 | `@ohos.data.relationalStore` | **仍是唯一真相源**（铁律 1） |

- **会话标识**：`sessionId = userId`（游客态为 `local-guest`），只有同 `sessionId` 的设备互相可见。
- **同步粒度**：**表级 + 行级**（以行 `id` 为最小单位合并）。
- **不依赖网络**：同一局域网 / 超级终端组网即可；**无服务端也能演示**。

### 12.3 协同合并协议

| 项 | 设计 |
|---|---|
| 方向 | 双向增量（拉 + 推合一） |
| 增量依据 | `updated_at > lastSymcAt`（本机 `device_info.last_sync_at`） |
| 冲突解决 | **LWW（Last-Write-Wins）**：`updated_at` 大者胜；相等时以 `device_id` 字典序大者胜（保证确定性） |
| 删除传播 | **软删除**（`is_deleted = 1` + `updated_at` 更新），删除也要能传播 |
| 幂等 | 以 `id`（UUID）为主键，重复合并不产生重复数据；**同一条碳记录不重复发分** |
| 封顶口径 | **本机已知流水判定；同步后发现超额不追回**，冲突计数 +1（见 §9.5 第 4 条） |
| 参与同步的表 | **9 张**：`carbon_record`、`point_record`、`user_goal`、`user_badge`、`user_purchase`、`user_appearance`、`science_progress`、`carbon_include`、`user_profile` |
| **不参与同步** | **10 张**：`device_info`、`sync_log`、`share_record`、`app_config`（本机专属）；`goal_def`、`badge_def`、`shop_item`、`science_article`、`carbon_factor_meta`（静态字典）；`point_daily_stat`（派生缓存） |
| 时钟偏移 | 合并前用对端时间戳与本机时间做偏移校正（取 ±5 分钟容差），避免因设备时间不准导致 LWW 反向 |
| 触发时机 | 手动点"立即同步"；设备在线且距上次 >5 分钟；配对成功后一次 |
| 失败处理 | 写 `sync_log` 状态 `failed`；**不更新 `last_sync_at`** |

### 12.4 协同状态面板（路演高光页）

展示字段：

| 字段 | 来源 |
|---|---|
| 设备列表（名称 / 型号 / 在线状态） | `DistributedDeviceManager` 实时查询 |
| 本机设备标识（后 6 位） | `device_info` |
| 对端设备记录条数 | 本次合并统计 |
| 聚合进度（发现 / 合并 / 回写） | `DistributedService` 运行时状态 |

| 冲突记录数 | 本次合并中 `updated_at` 被覆盖的条数 + 封顶超额次数（§9.5 第 4 条） |

## 第 15 章 · 工程与编码规范

### 15.1 命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 文件名（类/页面） | 大驼峰 | `CarbonService.ets` |
| 变量/方法 | 小驼峰 | `calculateReduction()` |
| 常量 | 全大写下划线 | `MAX_DAILY_RECORD_POINT` |
| 数据库表 | 小写下划线 | `carbon_record` |
| 数据库字段 | 小写下划线 | `factor_value` |
| 路由常量 | 全大写下划线 | `ROUTE_DASHBOARD` |
| 资源键 | 小写下划线 | `home_today_reduction` |

### 15.2 十条代码约束

1. **禁用 `any`**；禁用 `@ts-ignore`；禁用 `as` 强制类型断言（除 SDK 类型缺失处并在注释说明）。
2. **页面层禁止**业务计算与数据库读写；页面只能调 ViewModel。
3. **禁止跨层直连**：页面不得直接使用 Dao，必须经 Service。
4. **多表写入必须开事务**；事务边界在 Service 层。
5. **字符串与颜色应走资源**（`string.json` / `AppTheme`）。此项由铁律降级为规范：**端侧 AI、分享卡片等少数不可避免处允许字面量，但必须集中在一个文件并在注释中说明理由**。
6. **Canvas 组件必须处理空数据**（0 条记录时显示空态，不崩）。
7. **时间与数字格式化统一用** `DateUtil` / `Formatter`，禁止在页面拼格式。
8. **每个 Service 与工具类文件头部必须有注释块**：职责、对外方法、依赖、注意事项。
9. **每个目标/徽章的判定逻辑必须幂等**，重复调用结果一致、且不重复发分。
10. **积分发放必须在事务内**且受封顶约束；任何绕过 `PointService` 直接写 `point_record` 的代码视为严重违规。

> **v4.0 变更**：原铁律 6「零硬编码文案与颜色」降级为上述第 5 条（因引入端侧 AI 与分享卡片，存在不可避免的字面量）。

### 15.3 资源与构建

- `module.json5` 权限：**`ohos.permission.DISTRIBUTED_DATASYNC`**（分布式协同，**必需**）、`ohos.permission.INTERNET`（仅后台取价/备份，可选）、`ohos.permission.REMINDER_AGENT`（定时提醒）。**不申请**位置、通讯录、麦克风；**相机权限仅在启用识图拍照时申请**（仅选图则不需要）。
- 支持设备：`phone`（必须）、`tablet`（用于协同演示）。
- 构建配置：`compileSdkVersion: 12`、`compatibleSdkVersion: 12`、`runtimeOS: OpenHarmony`。
- 图标与启动图：`color_primary` 底 + 白色叶片/足迹，本地素材。

### 15.4 演示模式

- 设置页提供开关，开启后一键播种 `rawfile/demo/demo-seed.json`。
- **数值口径见附录 D §9**（与第 9 章积分规则一致）。
- 演示数据 `user_id = 'demo-user'`；关闭时按该 id 一键清除。

- 目的：避免路演"看板全空"，并为性能测试提供真实数据量。
